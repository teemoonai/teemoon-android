**Keyboard and paste**

- The composer field is now a `TextFieldState` field with a `contentReceiver` (`app/src/main/kotlin/ai/teemoon/app/DesignKit.kt`, the paste block around lines 1198–1231), so images arrive from a clipboard paste, from Gboard's copied-photo chip, and from keyboard stickers, Emoji Kitchen, Bitmoji and GIFs that a keyboard sends through `commitContent` as a content URI. All take the same route as a picked photo; a GIF arrives as its first frame; on a model that can't see images they take the can't-see route. Android hands no description with a sticker, so unlike iOS it stays an image rather than becoming text (`docs/ANDROID_NATIVE.md`).
- The paste rule (`app/src/main/kotlin/ai/teemoon/app/imaging/ComposerPaste.kt`): the clip is decided before anything goes into the field. When the clip has image items and the text beside them is nothing or a single URL, every image item attaches in clip order and no text goes in; any other text beside an image is pasted as text and nothing attaches. The clip's declared MIME types don't decide: an app-specific type or octet-stream is read like `image/*`, and the bytes' magic number decides. A clip whose text is one `data:` URL is an image, never text; a `data:` URL beside image items attaches after them. Typing, autocorrect, suggestions and dictation never read the clipboard.
- A pasted `data:` URL goes through the strict parser (`DataUrl.decode` in `app/src/main/kotlin/ai/teemoon/app/imaging/ImageGate.kt`): header exactly `image/(jpeg|jpg|png|gif);base64`, payload capped at 20 MiB, and the bytes' magic number must match the declared type; anything else is refused before any decoder, and no URL is ever fetched.
- The keyboard's action key is "send" (`ImeAction.Send`); a hardware return still breaks the line. `app/src/main/kotlin/ai/teemoon/app/DesignKit.kt`

**The isolated image decoder**

- Every image that enters the app (picker, camera, paste, keyboard, share-in, import) is decoded in `ImageDecodeService`, declared `android:process=":decode"`, `android:isolatedProcess="true"`, not exported: its own UID, no permissions, no app files, no network. Bytes go in and re-encoded pixels come out over two pipes (`app/src/main/aidl/ai/teemoon/app/imaging/IImageDecodeService.aidl`); the application object builds nothing in that process (`TeemoonApplication.kt`). A decode is abandoned after 15 s and the caller gets a placeholder. `app/src/main/kotlin/ai/teemoon/app/imaging/ImageDecodeService.kt`, `app/src/main/kotlin/ai/teemoon/app/imaging/IsolatedImageDecoder.kt`, `app/src/main/AndroidManifest.xml`
- JPEG, PNG, GIF and BMP are decoded by Wuffs v0.4.0-alpha.9 (memory-safe), compiled from the vendored single-file release into `libteemoon_wuffs.so` with a JNI shim that checks the header twice and the pixel and side caps again in C. `app/src/main/cpp/wuffs_jni.c`, `app/src/main/cpp/CMakeLists.txt`, `app/src/main/kotlin/ai/teemoon/app/imaging/WuffsImages.kt`
- WebP, HEIC/HEIF, AVIF and TIFF from a pick, paste or share are decoded by Android's `ImageDecoder` inside the same isolated process (`ImageDecodeService.platformFrame`): the decoder's detected MIME type must be the sniffed family (a lying container is refused as unsupported), the header size is checked against the same caps before allocation, decoding is software-only at the stored size, and the result is re-encoded to JPEG or PNG. Any failure, including a HEIC or AVIF that the isolated process's codecs can't open, is the "this image couldn't be read" note, never the input passed through. These formats are not memory-safe as Wuffs is; the process isolation is what holds a parser bug. The near.ai import never takes them: its `data:` parser accepts only JPEG, PNG and GIF. `app/src/main/kotlin/ai/teemoon/app/imaging/ImageGate.kt`
- The format comes from the magic number, never from a declared type or file name; `data:` URLs, sizes and pixel counts are gated in plain bounds-checked Kotlin before a decoder sees a byte. `app/src/main/kotlin/ai/teemoon/app/imaging/ImageGate.kt`

**Images on the phone model (Gemma 4)**

- Phone models read images (new in 1.1.0; 1.0.6 had no image input). Gemma 4 E2B and Gemma 4 E4B are both marked `readsImages` (`providers/src/main/kotlin/ai/teemoon/providers/LocalModelCatalog.kt`, `imagesOnDevice = true`), each behind a run-time memory check. A turn carries up to 10 images (the question's first, then the chat's earlier ones newest first), each re-encoded to a 768 px JPEG from the app's own stored bytes; any image bypasses conversation reuse. The vision executor is built only for a turn with an image. `app/src/main/kotlin/ai/teemoon/app/imaging/ImageHistory.kt`, `app/src/main/kotlin/ai/teemoon/app/imaging/OnDeviceImage.kt`, `inference/src/main/kotlin/ai/teemoon/inference/LiteRTTransport.kt`, `inference/src/main/kotlin/ai/teemoon/inference/LocalRuntime.kt`
- Run-time memory check instead of a supported-phone list (`providers/src/main/kotlin/ai/teemoon/providers/PhoneImageMemory.kt`): each model has a measured need per path — E2B NPU 2500 MB, GPU 3700 MB, CPU 2100 MB; E4B GPU 5000 MB, CPU 2100 MB (no NPU bundle carries E4B) — compared with this phone's ceiling (total memory less a 3000 MB system reserve, or the highest free memory the app has seen here, whichever is more) and with what is free now. Verdicts: permanent (the ceiling is under the need, or the OS killed an image turn of that model here) → the model is listed refused with "this phone doesn't have enough memory for images with <model>." and, where a smaller phone model fits, "use <smaller model>"; now → "<model> needs about X GB free for images; this phone has Y GB free right now. close some apps and try again."; else run. The ledger (highest free memory seen, killed model ids, the model of an image turn in flight) is in preferences. `app/src/main/kotlin/ai/teemoon/app/imaging/PhoneImageLedger.kt`, `inference/src/main/kotlin/ai/teemoon/inference/LocalRuntime.kt`
- Backend for image turns: the NPU bundles for the Tensor G5, Tensor G6 and Snapdragon 8 Elite (SM8750) now carry the vision encoder (`seesImages = true`), so those phones' image turns stay on the NPU with no second download; the warm-up on such a bundle also loads the image reader. On the general file, an image turn uses the GPU then the CPU only on a Google Tensor or Snapdragon 8-series chip (`BackendLadder.readsImagesOnGpu`: `SOC_MODEL` starting `sm8`, `tensor`, `gs` or `zuma`), and the CPU alone elsewhere, because two mid-range GPUs in the device pass named pictures wrong with no error; the emulator uses the CPU. The three NPU bundles themselves were already in 1.0.6 for text; only `seesImages` is new. `ondevice/src/main/kotlin/ai/teemoon/ondevice/BackendLadder.kt`, `providers/src/main/kotlin/ai/teemoon/providers/LocalModelStorage.kt`
- A phone still waiting on its second download says "no model on this phone reads images yet." in the where sheet. `providers/src/main/kotlin/ai/teemoon/providers/LocalModelCatalog.kt`
- The engine's load line on the generation chip (resident engine, first load, cached quick and slow, rebuild), held to `conformance/vendor/loading.json`. `app/src/main/kotlin/ai/teemoon/app/EngineLoadLine.kt`
