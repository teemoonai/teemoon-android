### Changed

**Who holds the key, and what teemoon checked**

- The trust screens say who holds the model key: "near.ai's key service decides which secure enclaves get that key". The expert screen adds that the key service derives the key for this app and that teemoon can't check that decision. `confidential/src/main/kotlin/ai/teemoon/confidential/KeyCustodyCopy.kt`
- Beside it, one sentence says what teemoon found for the enclaves near.ai listed, in five states: "teemoon checked every enclave near.ai listed.", "teemoon couldn't load near.ai's list of enclaves, so it couldn't check them.", "teemoon is checking the enclaves near.ai listed…", "teemoon couldn't finish checking the enclaves near.ai listed." and "one of the enclaves near.ai listed failed teemoon's check." The first is shown only when every listed check has answered and passed. `confidential/src/main/kotlin/ai/teemoon/confidential/KeyCustodyCopy.kt`
- The sealed row's mark and the expert screen's key node follow that state: checking is pending, a list that couldn't load or a check that couldn't finish is a soft note, and a failed listed enclave is a failure; none of them shows a check mark. `confidential/src/main/kotlin/ai/teemoon/confidential/TrustVerdict.kt`, `app/src/main/kotlin/ai/teemoon/app/TrustChain.kt`
- Lines that claimed more than the app checks are removed: no trust string says only the model can read the chat, that the key was made in or lives in one enclave, or that near.ai's gateway can't decrypt it. A test holds every trust string to that list. `app/src/main/kotlin/ai/teemoon/app/TrustPresentation.kt`, `app/src/main/kotlin/ai/teemoon/app/TrustScreen.kt`, `app/src/test/kotlin/ai/teemoon/app/KeyCustodyCopyTest.kt`
- The hero line with a quantisation reads "encrypted to <model>'s enclave key · <quant>". `confidential/src/main/kotlin/ai/teemoon/confidential/TrustVerdict.kt`
- A failed enclave list asks to "retry verification" instead of "still checking … wait". `confidential/src/main/kotlin/ai/teemoon/confidential/ConfidentialSession.kt`, `app/src/main/kotlin/ai/teemoon/app/SendChoices.kt`

**Reasons a send is held**

- When the enclaves near.ai lists hold a send, the reason names which: "teemoon couldn't load near.ai's list of enclaves for this model.", "another enclave near.ai lists for this model failed verification.", "another enclave near.ai lists for this model runs code its boot log doesn't match.", "near.ai lists an enclave for this model that holds a different key." or "near.ai's enclaves for this model name different key services for the same key." The read enclave's own lines are separate, so the reader learns it was another enclave. Held to `conformance/vendor/sendgate.json`. `confidential/src/main/kotlin/ai/teemoon/confidential/ModelCandidates.kt`
- A listed enclave whose Intel or NVIDIA check couldn't run names the listed enclaves, not the read enclave's line. `confidential/src/main/kotlin/ai/teemoon/confidential/AttestationSummary.kt`

**Send**

- "send unencrypted" is now "send without encryption", everywhere it appears. `app/src/main/kotlin/ai/teemoon/app/SendChoices.kt`
- A sent question glides to the top of the chat over 0.4 s (was 0.25 s), with the same smoothstep curve. `app/src/main/kotlin/ai/teemoon/app/Motion.kt`, `app/src/main/kotlin/ai/teemoon/app/Transcript.kt`

**Prices**

- List prices for your own OpenAI, Google, DeepSeek and Mistral keys are refreshed (snapshot 2026-11-19, 145 rows: 5 new models, 10 repriced). `providers/src/main/kotlin/ai/teemoon/providers/ListPriceSnapshot.kt`

### Security

Audit items for this release: the 1.1.0 audit's addendum of 2026-11-19 and its follow-up review. Audit pages: [teemoonai/audits](https://github.com/teemoonai/audits/tree/main/client/teemoon-android).

- A1, A2 — a quote's attestation key must be Intel's TD Quoting Enclave's: the QE report is signed by the PCK leaf certificate, its report_data is sha256 of the attestation key and the QE auth data, and the QE report matches Intel's TD QE identity, MISCSELECT included. Every enclave near.ai lists under the model's key goes through Intel DCAP like the read one, and a listed enclave with no quote fails. `confidential/src/main/kotlin/ai/teemoon/confidential/TdxQuote.kt`, `confidential/src/main/kotlin/ai/teemoon/confidential/DcapService.kt`
- A3 — each listed enclave's NVIDIA GPU evidence goes to NVIDIA's service against the list's nonce. `confidential/src/main/kotlin/ai/teemoon/confidential/NrasVerification.kt`
- A4 — each listed enclave gets the read enclave's trust scope: its action-log binding, its boot-log replay and the services it runs. Each quote of a record goes to Intel once; the listed verdicts and trust scopes share one DCAP pass. `confidential/src/main/kotlin/ai/teemoon/confidential/NearTrustScope.kt`
- A5 — the "reviewed" row is the worst across every enclave near.ai lists under the key, each scoped by everything its host runs. `confidential/src/main/kotlin/ai/teemoon/confidential/ModelNodeAuditPath.kt`, `app/src/main/kotlin/ai/teemoon/app/TrustPresentation.kt`
- A7 to A10, A12, A13 — the copy and reasons above (see Changed). A13: listed enclaves that hold one key must name one key service; the key provider and mr-kms are compared. A model with an empty name asks for no list, and the listed state never stays "checking" past the verdict deadline. `confidential/src/main/kotlin/ai/teemoon/confidential/ModelCandidates.kt`
- A11 — near.ai's list of enclaves is capped at 4 MB while it streams and at 8 entries (a longer list counts as a list that didn't load), and its request is cancelled at its 15 s limit and with its caller. `confidential/src/main/kotlin/ai/teemoon/confidential/AttestationService.kt`
- A15 — each listed-enclave behaviour is pinned by a test that its mutant turns red, including the four mutants that survived an earlier 1.1.1 candidate. `confidential/src/test/kotlin/ai/teemoon/confidential/CandidateMutantPinsTest.kt`
- B1 (the 1.1.0 audit's accepted LOW) — a near.ai model you've sent to sealed asks once before its first plain send: "<model> isn't end-to-end encrypted anymore", "near.ai now lists it as running outside its own enclaves, so this message would reach near.ai over ordinary TLS. your earlier messages to it were sealed.", with "send without encryption" and "don't send". A model counts as sent to sealed when its sealed request reaches the wire; "send without encryption" removes it, so later plain sends to it don't ask; an earlier confirmation never answers this ask. The list holds model ids only, in the app's preferences (no chat, key or content, no schema change); deleting the near.ai provider clears it. `confidential/src/main/kotlin/ai/teemoon/confidential/TierDowngrade.kt`, `inference/src/main/kotlin/ai/teemoon/inference/OpenAiTransport.kt`
- A model key with no readable quote blocks the send, with the existing unbound-key reason; it used to read "still checking" and offer to send anyway, sealed to a key nobody had checked. `confidential/src/main/kotlin/ai/teemoon/confidential/ConfidentialSession.kt`
- C3 — the release workflows run `tools/check_store.py` from the tag's own tree, so the APK and its check come from the same commit; the public assembly now fails a tree whose workflows fetch a file from another commit, download raw repository content, or run a script from the runner's temp directory (see Build & CI).

### Moved to 1.1.2

- B8 to B19, the 1.1.0 audit's remaining INFO items: the share and paste URI gate, a size cap on the import staging copy, bounds on the isolated decoder's reply, an allow-list for unsealed request fields in place of the deny-list (B14), validation of the action log's commit and file strings before they go into a URL, log hygiene (turn warnings, the search-index failure line), the credits list, and screenshot seams. Each stays as described in [the 1.1.0 notes](1.1.0.md#security).
- B1's explicit backup excludes: naming each data domain under cloud backup and device transfer. Backup is already off for the whole app (`android:allowBackup="false"`), so this changes no behaviour.
- B1's fail-safe for an unreadable list: in 1.1.1, if the app can't read its list of models sent to sealed, the list counts as empty, so the ask above doesn't come.
- A TLS pin for near.ai's gateway.

### Build & CI

- `release-build.yml` and `release-verify.yml` run `python3 tools/check_store.py github` from the checked-out tag again. 1.1.0's tag had no `tools/check_store.py`, so `main` carried a CI-only commit (`35766b6`) that fetched the script from the dispatching commit into the runner's temp directory; 1.1.1 carries the script, and that step is removed.
- Re-verifying `v1.1.0-3918` needs the release workflows as they were at `35766b6`; 3918's verified verdict stands and was not re-run.

### Known issues

- near.ai's key service decides which enclaves get a model's key, and teemoon checks only the enclaves near.ai lists. An enclave the key service admits that near.ai doesn't list can hold the key, and teemoon can't see it; near.ai has to fix that (audit D1, the 1.1.0 addendum MEDIUM narrowed to unlisted enclaves).
- near.ai's quotes are not bound to the caller (audit D3).
- The TLS connection to near.ai's gateway is not bound to an attested enclave (audit D4); a gateway TLS pin is planned for 1.1.2.
- The B8 to B19 items, B1's backup excludes and the unreadable-list fail-safe ship in 1.1.2 (above).
- R8/minify is still off for the release build, which draws Play's obfuscation notice; fix by February 2027.
- Some `ports.json` citations name teemoon-ios development commits that are not in any public iOS tag, so they can't be resolved against the public iOS repository (stated in `README.md`).
